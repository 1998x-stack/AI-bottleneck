# AI × 小说生产：关键 Issues、根因、瓶颈与解决方案深度研究

**研究日期：**2026-11-17  
**覆盖范围：**中文网络长篇、类型小说、AI 辅助写作、Agent 自动创作、编辑审校、平台发行与 IP 衍生。  
**定位：**可用于产品立项、架构设计、技术评审与实证测试的研究文档（不是平台合规或版权法律意见）。  
**证据原则：**分清已发表研究、官方规则、产品说明、作者访谈与待验证的工程判断。

> **一句话结论：**现阶段 AI 小说生产最大的系统性障碍，不是单章的写作速度，而是长篇状态一致性、宏观叙事质量、创造性同质化与评价可靠性的联合缺陷；将它们带入生产流程后，又会形成昂贵的人工返工、平台合规及版权不确定性。没有可验证的生产与质量闭环，快速生成越多，潜在返工和风险也可能越多。

## 0. 执行摘要：最值得优先解决的五件事

1. **长期记忆与叙事状态治理（P0）：**小说不是“带摘要的聊天记录”。需要区分客观事实、角色信念、传闻、隐藏真相与尚未发生的计划，按事件维护随时间变化的角色、道具、地理、势力和世界规则。ConStory-Bench 在 2,000 个测试提示中系统定义了 5 类、19 个子类的一致性错误，指出事实与时间维度尤为突出。[S02]
2. **全书结构与人物弧线（P0）：**章节写得流畅不等于长篇好看。2026 年 LitVISTA 研究显示，模型理解叙事功能与全局结构仍存在系统性不足；中国网文蓝皮书也指出整体规划、后期节奏、人物关系膨胀等行业问题。[S03][S01]
3. **质量评测与编辑成本（P0）：**不能把“另一个大模型给了 9/10 分”当作验收。LitBench 的强通用模型评委在人类偏好比较中约达 73% 一致率；中文整本小说 ChangJuan 的 Kendall τ 相关性仍有限。评价必须分成可验证硬约束、专业编辑判断和真实读者盲测。[S05][S04]
4. **原创性与版权治理（P0）：**模型的情节组合可能跨样本重复；AI 洗稿还可能在表层文本不同的情况下继承人物关系和核心情节。2026 年中国作家网专题报道了网文 IP 的此类侵权与跨平台改编难题。[S06][S13]
5. **平台可发行性与商业单位经济（P0）：**各平台对 AI 生成内容的声明、允许范围、签约要求不同。与其计算“每百万生成字数成本”，不如计算“每万字合格定稿的综合成本、人工修改时长与读者表现”。中国标识规则、晋江用户协议与 KDP 的 AI 内容定义需要分平台落实。[S14][S15][S17]

**本报告的排序不是‘行业故障发生率统计’。**目前未找到跨平台、同口径、覆盖作者群体的公开故障频率调查。这里使用“证据强弱 × 严重性 × 传播范围 × 治理可行性”的定性优先级，须由后续实测校准。

## 1. 证据分层与研究边界

| 证据等级 | 定义 | 如何使用 |
|---|---|---|
| A | 同行评审的直接实验、正式官方报告或平台一手规则 | 可支持具体结论，但不得外推到所有作品/模型 |
| B | 预印本、产品官方技术文档、可靠行业报道 | 可用于方案设计，注意厂商自述及案例偏差 |
| C | 作者社区讨论、媒体体验文章和工程经验 | 用于发现问题与设计访谈，不用于估算发生率 |
| H | 本文提出、尚无充分直接实测的工程假设 | 必须给出可证伪的实验与验收指标 |

**关键区分：**
- 中文网文行业的“套路化、仓促收尾、人物扁平”不是 AI 独有缺陷；不能把行业问题全部归因于模型。[S01]
- 英文短篇的模型/读者实验不能直接推断中文百万字连载的真实质量；跨语言、长度、题材均需重新评测。[S05][S06][S21]
- 基准上的模型排名不等同于产品可用性；真实流程还受上下文管理、人工修改、数据权限和发布条款约束。
- Reddit 及作者社区反馈有价值，但存在选择偏差；不据此宣称“XX% 作者遇到问题”。[S19]

### 2.1 三种“最大”的定义

- **最大技术故障源：**I01/I02/I07/I08——文本生成没有稳定的外部真相与时间化状态。
- **最大最终质量瓶颈：**I03/I04/I05/I10——局部流畅与全局优秀之间存在鸿沟。
- **最大商业阻断因素：**I15/I17/I19/I20——内容完成不等于具备合法和经济可行的发行条件。

## 3. 技术根因一：长篇记忆不等于长上下文

### 3.1 典型故障

第 17 章角色左手受伤；第 41 章右手又被描述为唯一可用之手；第 86 章出现未解释的双手持剑。又如角色在故事第 3 天才知道秘密，却在故事第 2 天的插叙中准确引用秘密。这些分别属于状态矛盾、时间因果与认知边界错误。

ConStory-Bench 不仅关注人物设定，也涵盖事实细节、叙事风格、时间情节与世界规则五大方面；其研究发现，事实类和时间类错误偏多，部分错误集中于故事中段。[S02]

### 3.2 为什么简单 RAG 不足够

一段历史正文可以同时包含作者旁白、角色误解、谎言、假设、推理与尚未成真的计划。普通向量检索只回答“文本看上去相关吗”，不能直接回答“这个事实在当前故事时间是否仍有效、是谁知道的、可信程度如何”。

同时，长上下文并不保证信息被正确使用。经典 *Lost in the Middle* 实验发现，模型对上下文不同位置的信息利用存在差异；该研究原任务并非小说，因此只能支持检索设计上的警示，而非直接说明所有现代小说模型都具有相同比例的错误。[S08]

### 3.3 解决方案：带证据的双时间状态库

推荐最小结构：

```json
{
  "fact_id": "fact_0086",
  "entity_id": "character_01",
  "predicate": "left_arm_status",
  "value": "lost",
  "world_time_from": "day_16",
  "world_time_to": null,
  "narrated_in_chapter": "chapter_086",
  "epistemic_type": "objective_fact",
  "known_by": ["character_01", "character_07"],
  "source_span": "chapter_086:para_140-143",
  "status": "approved",
  "supersedes": "fact_0031"
}
```

**实现原则：**
1. `canon`（作者确认的客观事实）与 `belief`（角色相信之事）分开存储。
2. 保留世界发生时间与读者获知时间，避免倒叙/悬疑认知错位。
3. 所有状态变更必须有原文证据片段及版本号。
4. 草稿阶段的模型提取仅为候选状态，不自动污染正式设定。
5. 冲突时优先查看事件历史和人工签核，而不是覆盖旧记录。
6. 召回使用结构化查询、关键词检索与语义检索混合，并评估误召回。

ConWriter 的场景级写作、动态记忆、符号状态验证和局部修复，为这种控制策略提供了研究依据；Topo-Narrator 把人物图、剧情链和环境树分开，也说明“一个大摘要”不是唯一合理表示方式。[S09][S10]

### 3.4 可执行验收

- **关键事实冲突率**：抽查确认的严重矛盾数 / 每 1 万字，保留置信区间。
- **约束召回率**：写章节前，应召回的关键历史事实中被召回的比例。
- **事实污染率**：未经人工确认而被写入 canon 的错误事实占比。
- **误报率**：对合理误导、撒谎、魔法规则例外误判为硬冲突的比例。
- **回滚正确率**：章节撤回后，状态视图能否恢复到撤回前。

## 4. 技术根因二：局部连贯不等于整体叙事成功

### 4.1 三类失效

**（a）无目标的场景堆砌。**一个又一个场景看似有冲突，但对人物命运和核心主题没有净增量。  
**（b）节奏曲线机械化。**每章结尾都悬念，但缺少铺垫、缓冲与代价，读者很快习惯这种刺激。  
**（c）角色成长伪进化。**人物只是在能力、装备或地位上变强，却没有发生价值观与选择机制的变化。

LitVISTA 发现，模型在叙事事件锚点、功能与结构整体把握方面仍存在系统性困难，即便增强推理也不是稳定有效的万能方案。[S03]

### 4.2 解决方案：从故事承诺倒推场景

每个场景采用 `GOAL → OBSTACLE → CHOICE → CONSEQUENCE → STATE DELTA`：

| 字段 | 核查问题 |
|---|---|
| Goal | 此场景谁想要什么，为什么此刻必须要？ |
| Obstacle | 冲突是来自对手、世界规则还是角色内在弱点？ |
| Choice | 角色做出哪个具体、不可替代的选择？ |
| Consequence | 选择带来什么真实代价、反作用或信息变化？ |
| State Delta | 人物关系、信息、资源或能力有哪些持续变化？ |

每一卷应明确“阶段性失败/成功、价值观变化、主要关系变化、高潮代价、伏笔推进”；而不是只设定章节数与字数。

### 4.3 编辑层面的结构审查

- 先审 **全书冲突和人物弧线**，再审卷纲与章节，最后审句子；避免局部润色掩盖结构失败。
- 建立事件因果图：每个重大转折都应能追溯必要前置事件；允许巧合，但不能反复用巧合解决核心冲突。
- 设“无功能场景”诊断：如果移除某场景对人物、因果、信息、主题均无影响，则标记人工复审。
- 对连载题材评估读者的“继续阅读理由”，但不要把所有文学形式简化为爽点计数器。

## 5. 创造性与文学质量：为什么 AI 味会变成生产瓶颈

### 5.1 证据比常见口号复杂

2025 年 PNAS 论文 *Echoes in AI* 对短故事进行比较，发现模型多次生成会重复部分情节元素，且跨模型亦有相似组合；该研究说明“情节多样性风险”，但**不能直接证明每部 AI 小说均缺乏原创性或构成法律抄袭**。[S06]

2026 年 *Nature Human Behaviour* 研究汇总多个数据集与场景发现，大模型润色/改写和语言多样性下降有关。这是跨领域文本研究，可作为小说风格同质化的警示，但不应把它的具体数值直接外推到小说。[S07]

读者研究并非一边倒：有研究发现，AI 故事在短文本盲评里不一定比真人差，但标注“AI 所作”可能影响评价；另一项研究发现，部分读者的“进入故事世界”感更弱。不同样本、提示、体裁、标签条件会导致相反结论。[S21][S22]

### 5.2 症状与根因对照

| 症状 | 可能根因 | 不宜采用的伪解决方案 | 更可靠做法 |
|---|---|---|---|
| 全文充满抽象感悟 | 没有明确行动与选择 | ‘减少 AI 味’万能提示词 | 用具体行为承载情绪 |
| 对白所有人同声 | 角色声音未结构化 | 随机插入口头禅 | 角色语用目标/教育背景/禁用表达 |
| 冲突过于方便 | 大纲没有预先设定代价 | 要求“更曲折” | 限制角色资源与可用路径 |
| 每个高潮同一套路 | 只对即时刺激优化 | 每章随机反转 | 维护卷级情绪曲线和后果 |
| 原创性不足 | 生成候选空间过窄 | 同义词替换、洗稿 | 跨题材因果重组、作者原创事实输入、盲评 |

### 5.3 关键决策

**AI 负责候选结构、错误定位和表达建议，作者保留决定作品独特性的核心判断。**对于文学性较强的作品，允许使用“AI 只提问/诊断，不改写正文”的工作模式。

## 6. 质量评测的三层陷阱

### 6.1 自动裁判不是“客观真理”

LitBench 含 43,827 对训练比较与 2,480 对测试比较，其结果显示：当时最强现成评委模型的判断与人类偏好约 73% 一致，专训评判模型提升至约 78%。注意：这是该基准及模型条件下的结果，不是全部小说评价的通用准确率。[S05]

面向中文整本小说的 ChangJuan 整理了 300 部小说及人类评分、读者评价，提出面向长书的分维度评估方法；其论文报告相关性从 Kendall τ = 0.248 提升到 0.341，说明长书评价存在很大的改进空间。[S04]

### 6.2 必须分离的审查层

1. **机器硬约束层：**人物生死、位置、库存、时间、公开设定的规则；要求有证据。
2. **文本编辑层：**重复、冗余、对白不自然、视角跳变、信息交代失衡；多数仅能提出建议。
3. **文学与读者层：**人物吸引力、代入感、出人意料但合理的情节、主题和风格；必须引入人类判断与真实阅读实验。

不要将所有层级压成一个“AI 小说综合得分”。硬约束失败具有发布阻断权；文学评价则应允许分歧。

### 6.3 评委治理

- 自动评委对事实类问题必须输出`claim + contradicting_span + supporting_span + rule_id`。
- 不允许让生成模型对自身章节的主观好坏直接做唯一裁判。
- 评估提示词、温度、模型版本及样本顺序必须记录，避免结果漂移。
- 对风格、情绪和原创性使用至少两名真人盲评，记录评价者之间的一致性。
- 提供复核队列：评委意见相互矛盾、证据不足或存在叙事性误导时转人工。

## 7. 人机协作与 Agent 工作流的隐性成本

### 7.1 生产线最危险的失败形式

`写作 Agent`生成错误人物状态 → `摘要 Agent`错误概括 → `Memory Agent`将其当成正史 → `下一章节 Agent`基于错设定扩展 → `Editor Agent`只看局部文本继续润色。

这是一种**状态污染级联**：多 Agent 并不天然更可靠，有时反而为错误提供了多轮确认的错觉。[S09][S10]

### 7.2 推荐的治理闭环

```text
作者批准 Story Bible
       ↓
Planner 创建章节契约
       ↓
Retriever 组装证据与状态
       ↓
Writer 按场景生产候选文本
       ↓
Extractor 生成候选状态变化
       ↓
Verifier 核验硬约束与引用证据
       ├─ 失败 → 局部重写 → 重新验证
       ↓
Editor 评估叙事与风格
       ↓
作者批准章稿及状态变更
       ↓
提交不可变章节版本 / 更新正式事实视图
```

必须具有：事务性提交、幂等任务、模型调用日志、改稿差异比较、失败重试上限、状态回滚和人工最后裁决权。

### 7.3 人工负担是否真正降低？

对一个 5 万字测试故事，建议追踪：起草人工分钟数、核查分钟数、修订分钟数、事实维护分钟数、反复生成分钟数、最终作者接受率。若 AI 缩短草稿时间但大幅增加核查工作，实际效率可能并未提高。

## 8. 原创性、AI 洗稿与法律/平台风险

### 8.1 最需要区别的三件事

- **模型生成的常见套路相似：**可能是类型惯例，不自动构成版权侵权。
- **对他人具体表达的实质性挪用：**可能涉及著作权争议，需要结合具体权利、事实和法域判断。
- **无法证明人类创作贡献：**可能影响部分法域下的版权登记或权利主张。

2026 年中国作家网转引的网文产业调查描述了 AI 洗稿、人物关系与核心情节链条挪用、跨平台漫剧化的侵权争议及举证困难。这是已报道的案例，不代表所有 AI 创作流程都会侵权。[S13]

美国版权局 2025 年报告认为，AI 辅助作品可以获得版权保护，但仅靠提示词并不足以使纯 AI 输出自动满足人类作者贡献要求；具体权利认定必须按适用法律分析。[S16]

### 8.2 平台规则并不统一

- **中国标识制度：**《人工智能生成合成内容标识办法》自 2025-09-01 实施；用户在网络信息内容传播服务中发布生成合成内容，有相关声明和标识义务，具体适用须按角色及服务场景判断。[S14]
- **晋江：**其用户注册协议要求上传或发布人工智能生成合成内容时显著标识，平台可以采取检测与处置；其具体原创写作规范还需结合签约及公告核对。[S15][S13]
- **Amazon KDP：**正式规则明确区分 AI-generated 和 AI-assisted；AI 生成文本即使后来大量修改，仍可能属于需申报的 AI-generated，单纯辅助改稿的定义不同。[S17]

建议为每个平台建立 `policy_snapshot`（规则链接、抓取时间、适用作品形态、待人工确认事项），在每次发布前重新核验。

### 8.3 为什么不能依赖 AI 检测器定罪

AI 检测器根据文本统计特征推断，不是直接读取文本生产历史。2026 年关于检测器的研究与案例提醒，单个分数可能受文本风格、改写和样本影响；应保存草稿版本、编辑记录和人工创作说明，而非以单次检测作为高风险处置的唯一依据。[S20][S18]

**建议：**保留原始草稿、关键人工变更、模型调用范围、素材权利证明和成稿版本哈希；对侵权风险采取“人工复核 + 版权专业意见 + 证据保存”，不提供规避检测的洗稿流程。

## 9. 数据安全与生产可用性

稿件、未发布 IP 设定、商业计划、签约信息和作者隐私属于高敏感业务资产。系统应提供：租户隔离、最小权限、日志脱敏、加密存储、模型供应商留存策略核验、可配置的数据保留/删除、导出与撤销授权；引用第三方内容要有许可依据。面向公众提供生成式 AI 服务还可能涉及中国现行生成式 AI 服务规定。[S25]

**工程失败场景：**同一创作工作室的两个作者，其角色知识库检索结果串库。此类问题哪怕发生一次，也可能构成严重的商业信誉和保密事故。必须通过租户隔离测试，而不是靠提示词声称“不要泄露”。

## 10. 现有方案能力与缺口

| 方案/研究 | 已有解决思路 | 仍需核验的缺口 |
|---|---|---|
| Novelcrafter Codex | 人物/设定条目、别名识别、上下文注入规则 [S11] | 角色知识状态是否随事件自动准确迁移；是否可验证事实证据 |
| Sudowrite Story Bible | 从设定、概要、角色到场景与正文的依赖链 [S12] | 超长篇状态更新、客观约束阻断与跨章证据追踪 |

| ConWriter | 场景级生成、动态记忆、符号约束、局部修复 [S09] | 大规模长期连载、多作者协作和真实读者偏好 |
| Topo-Narrator | 人物图、剧情链、环境树异构记忆 [S10] | 工程复杂度、跨类型泛化和生产运维成本 |

**判断：**市场存在不少“AI 写作工作台”，但“带版本和证据的叙事状态库 + 反事实检查 + 中文整本小说评估 + 作者可控修订”的组合更值得独立验证。此判断属于产品机会假设，并非已证实的市场空白。

## 11. P0/P1/P2 解决方案路线图

### P0：可验证的生产闭环

**范围：**一个题材、一个主作者、一部 3–5 万字测试故事；先实现可用的事件日志、角色事实、章契约、人工审批、引用式矛盾检测与回滚。

**交付物：**`story.schema.json`、`character.schema.json`、`event.schema.json`、`chapter_contract.schema.json`、`continuity_rules.yaml`、可审查的章节与版本变更记录。

**退出条件（建议性目标，不是行业基准）：**关键事实的可追溯率 > 95%；所有发布章节有作者确认状态；零个未经确认的机器候选事实进入正式 canon；任何失败章节可回滚至前一批准版本。

### P1：叙事质量与成本优化

**范围：**伏笔 DAG、全书节奏仪表板、人物动机曲线、独立编辑 Agent、局部修订、检索质量测试和人工盲评。对照简单提示词基线量化收益。

**退出条件：**在相近预算和人工投入下，严重矛盾更少，盲评不显著劣于基线；若无改善，停止增加 Agent 数量并分析检索/评委误差。

### P2：多作品和发行生态

**范围：**多租户、团队协作、出版商权限、平台政策快照、发布前申报核查、合规留痕、有声书/翻译/剧本/分镜派生接口。

**退出条件：**作者愿意反复使用，作品按时完成，单位合格定稿成本可控，具备真实发行闭环及版权链条。

## 12. 建议执行的对照实验（研究而不是营销演示）

### 12.1 实验假设

- H1：结构化状态+证据检索，能够比“仅添加长摘要”更有效降低关键事实矛盾。
- H2：场景契约+卷级规划，能够改善全书叙事连贯性，但未必提高独创性。
- H3：自动评委的事实错误检测能力高于其评估文学吸引力的可靠性。
- H4：随着章节增加，未经验证的状态污染将显著增加编辑返工。
- H5：增加 Agent 不必然提高单位合格定稿效率。

### 12.2 四组系统对照

| 实验组 | 方法 | 用来回答的问题 |
|---|---|---|
| A | 直接 Prompt + 最近章节 | 单模型起点表现 |
| B | 全书大纲 + 定期摘要 + RAG | 常见工程方案是否足够 |
| C | B + 状态机 + 时间线 + 引用式检查 | 结构化一致性治理收益 |
| D | C + 分层编辑 + 人工审核闸门 | 完整协同流程净收益 |

建议先运行小规模 pilot：2 类题材 × 2 个长度档 × 2 个随机种子 × 4 组 = 32 部测试文本。长度档和读者工作量可根据预算确定。确保四组拥有同类选题、相近预算、同一评价规则，并随机化作品顺序。

### 12.3 核心指标定义

| 指标 | 定义 / 注意事项 |
|---|---|
| Hard Contradictions / 10k | 每 1 万汉字的人工复核严重硬矛盾数量 |
| Evidence-grounded Precision | 自动标注矛盾中经人工确认的比例 |
| Evidence-grounded Recall | 预先植入矛盾集合中被正确找出的比例 |
| State Drift | 当前事实与原 canon 不一致但未经批准的状态数量 |
| Arc Quality | 人类读者盲评情节因果、高潮铺垫与收束；分维度量表 |
| Voice Distinctiveness | 混合台词中识别不同角色声音的正确率（作为代理指标） |
| Edit Minutes / Accepted 10k | 每万字合格定稿所需人类编辑时间 |
| Net Cost / Accepted 10k | API、基础设施、人力及重试费用除以验收字数 |
| Reader Continuation Intent | 看完节选后愿意继续阅读的比例（不等于真实付费） |
| Platform Compliance Pass | 每个平台发布前应披露/授权/审核项完成比例 |

**因果识别注意：**同一题材中不同故事本身的吸引力差异很大；使用匹配创意简报、足够多随机种子、盲评与置信区间，避免用一部优秀作品作“全面领先”的证据。

## 13. 推荐的系统架构与数据结构

```text
interfaces/
  author_studio/      # 作者工作台：审批、差异、故事地图
  editor_console/     # 编辑核查：证据、问题、分配
services/
  story_planner/      # 总纲、卷纲、章/场景契约
  story_writer/       # 模型适配、场景候选与重写
  state_extractor/    # 事件/状态候选抽取
  story_memory/       # canon/belief/rumor/time/knowledge
  continuity_checker/ # 规则引擎、检索证据、冲突定位
  literary_editor/    # 分层评审、风格评测、建议
  policy_guard/       # 平台规则、版权与披露清单
  experiment_lab/     # 基线、盲评、统计与回归
storage/
  manuscripts/        # 版本化正文
  evidence_spans/     # 证据片段、版本哈希
  story_events/       # 不可变事件日志
  state_views/        # 按角色和时间聚合的状态视图
  publication_logs/   # 发布审定与平台政策版本
```

### 13.1 数据模型中的关键字段

- `source_span`, `source_hash`: 事实和审校结论能定位到哪一版的哪一段。
- `world_valid_from/to`: 事实在故事世界生效的时间区间。
- `narrative_revealed_at`: 读者在何处被告知。
- `known_by`, `belief_holder`: 角色认知权限与误解来源。
- `canon_status`: candidate / reviewed / approved / superseded。
- `agent_run_id`, `model_version`, `prompt_version`: 可审计的生产溯源。
- `editor_decision`, `reason`: 人类决定与原因。
- `rights_basis`, `distribution_policy_version`: 素材权利基础和发行规则快照。

### 13.2 质量门禁

```text
DRAFT -> STRUCTURAL_REVIEW -> CONTINUITY_REVIEW
      -> EDITOR_REVIEW -> AUTHOR_APPROVAL
      -> CANON_COMMIT -> DISTRIBUTION_CHECK -> PUBLISHED
```

**规则：**机器可以提出候选事实和问题，但不能越权将其视为作者定稿。审校失败默认产生局部修复任务，超过重试预算即转人工。严禁为通过审校而改写既定剧情事实。

## 14. 商业化判断：优先做哪种产品

**第一选择：小说一致性审校与记忆工具。**面向已拥有正文的作者，支持导入、角色/事件抽取、跨章矛盾定位、引用式修改建议与人工确认。其价值可直接通过节省编辑时间与错漏下降验证。

**第二选择：中文长篇编辑工作台。**融合卷级结构诊断、角色弧线、伏笔图谱、风格对比和真实读者测试；在工具侧保留作者表达，而不是追求代笔率。

**第三选择：从小说到 IP 衍生的资产中台。**长期价值较大，但必须建立授权链、视觉与剧情统一资产，且面临更多平台和合作方依赖。

**不建议作为起点：**以“几分钟自动写百万字”为主卖点的无人工验收平台。这可能带来短期演示效果，但难以证明真实阅读价值、改稿效率与可持续发行能力。

## 15. 待进一步调查的问题与数据缺口

1. 中文 30 万字以上的 AI 协同创作，有没有公开、统一、可复现实验数据？目前证据明显不如英文短篇和一般文本任务充分。
2. 不同细分题材（玄幻、悬疑、言情、历史、科幻）的一致性错误和读者偏好是否不同？
3. “先生成后检查”与“生成时执行约束”谁更经济？应在相同预算下比较。
4. 人工编辑环节究竟节省还是转移了劳动？需要真实使用日志而非访谈回忆。
5. 机器评审能否提升真实平台的读者追更和付费？不能用模型分数替代经营结果。
6. 创作过程证据如何以尽量低成本同时服务版权申报、合规与纠纷举证？
7. 多媒体衍生时，故事资产对漫画/短剧创作效率的提升能否达到可出售的水平？
