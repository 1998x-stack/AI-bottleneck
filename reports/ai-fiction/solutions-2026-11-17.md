# AI × 小说生产：关键 Issues、根因、瓶颈与解决方案深度研究

**研究日期：**2026-11-17  
**修订版本：**v2.0（新增 I01—I20 现有方案、工程落地和测试验收）  
**覆盖范围：**中文网络长篇、类型小说、AI 辅助写作、Agent 自动创作、编辑审校、平台发行与 IP 衍生。  
**定位：**可用于产品立项、架构设计、技术评审与实证测试的研究文档（不是平台合规或版权法律意见）。  
**证据原则：**分清已发表研究、官方规则、产品说明、作者访谈与待验证的工程判断。

> **一句话结论：**现阶段 AI 小说生产最大的系统性障碍，不是单章的写作速度，而是长篇状态一致性、宏观叙事质量、创造性同质化与评价可靠性的联合缺陷；将它们带入生产流程后，又会形成昂贵的人工返工、平台合规及版权不确定性。没有可验证的生产与质量闭环，快速生成越多，潜在返工和风险也可能越多。

## 0. 执行摘要：最值得优先解决的五件事

1. **长期记忆与叙事状态治理（P0）：**小说不是“带摘要的聊天记录”。需要区分客观事实、角色信念、传闻、隐藏真相与尚未发生的计划，按事件维护随时间变化的角色、道具、地理、势力和世界规则。ConStory-Bench 在 2,000 个测试提示中系统定义了 5 类、19 个子类的一致性错误，指出事实与时间维度尤为突出。[S02]
2. **全书结构与人物弧线（P0）：**章节写得流畅不等于长篇好看。2026 年 LitVISTA 研究显示，模型理解叙事功能与全局结构仍存在系统性不足；中国网文蓝皮书也指出整体规划、后期节奏、人物关系膨胀等行业问题。[S03][S01]
3. **质量评测与编辑成本（P0）：**不能把“另一个大模型给了 9/10 分”当作验收。LitBench 的强通用模型评委在人类偏好比较中约达 73% 一致率；中文整本小说 ChangJuan 的 Kendall τ 相关性仍有限。评价必须分成可验证硬约束、专业编辑判断和真实读者盲测。[S05][S04]
4. **原创性与版权治理（P0）：**模型的情节组合可能跨样本重复；AI 洗稿还可能在表层文本不同的情况下继承人物关系和核心情节。2026 年中国作家网专题报道了网文 IP 的此类侵权与跨平台改编难题。[S06][S13]
5. **平台可发行性与商业单位经济（P0）：**各平台对 AI 生成内容的声明、允许范围、签约要求不同。与其计算“每百万生成字数成本”，不如计算“每万字合格定稿的综合成本、人工修改时长与读者表现”。中国标识规则、晋江用户协议与 KDP 的 AI 内容定义需要分平台落实。[S14][S15][S17]

**本报告的排序不是‘行业故障发生率统计’。**目前未找到跨平台、同口径、覆盖作者群体的公开故障频率调查。这里使用“证据强弱 × 严重性 × 传播范围 × 治理可行性”的定性优先级，须由后续实测校准。

## 1. 证据分层与研究边界

| 证据等级 | 定义 | 如何使用 |
|---|---|---|
| A | 同行评审的直接实验、正式官方报告或平台一手规则 | 可支持具体结论，但不得外推到所有作品/模型 |
| B | 预印本、产品官方技术文档、可靠行业报道 | 可用于方案设计，注意厂商自述及案例偏差 |
| C | 作者社区讨论、媒体体验文章和工程经验 | 用于发现问题与设计访谈，不用于估算发生率 |
| H | 本文提出、尚无充分直接实测的工程假设 | 必须给出可证伪的实验与验收指标 |

**关键区分：**
- 中文网文行业的“套路化、仓促收尾、人物扁平”不是 AI 独有缺陷；不能把行业问题全部归因于模型。[S01]
- 英文短篇的模型/读者实验不能直接推断中文百万字连载的真实质量；跨语言、长度、题材均需重新评测。[S05][S06][S21]
- 基准上的模型排名不等同于产品可用性；真实流程还受上下文管理、人工修改、数据权限和发布条款约束。
- Reddit 及作者社区反馈有价值，但存在选择偏差；不据此宣称“XX% 作者遇到问题”。[S19]

### 2.1 三种“最大”的定义

- **最大技术故障源：**I01/I02/I07/I08——文本生成没有稳定的外部真相与时间化状态。
- **最大最终质量瓶颈：**I03/I04/I05/I10——局部流畅与全局优秀之间存在鸿沟。
- **最大商业阻断因素：**I15/I17/I19/I20——内容完成不等于具备合法和经济可行的发行条件。

## 3. 技术根因一：长篇记忆不等于长上下文

### 3.1 典型故障

第 17 章角色左手受伤；第 41 章右手又被描述为唯一可用之手；第 86 章出现未解释的双手持剑。又如角色在故事第 3 天才知道秘密，却在故事第 2 天的插叙中准确引用秘密。这些分别属于状态矛盾、时间因果与认知边界错误。

ConStory-Bench 不仅关注人物设定，也涵盖事实细节、叙事风格、时间情节与世界规则五大方面；其研究发现，事实类和时间类错误偏多，部分错误集中于故事中段。[S02]

### 3.2 为什么简单 RAG 不足够

一段历史正文可以同时包含作者旁白、角色误解、谎言、假设、推理与尚未成真的计划。普通向量检索只回答“文本看上去相关吗”，不能直接回答“这个事实在当前故事时间是否仍有效、是谁知道的、可信程度如何”。

同时，长上下文并不保证信息被正确使用。经典 *Lost in the Middle* 实验发现，模型对上下文不同位置的信息利用存在差异；该研究原任务并非小说，因此只能支持检索设计上的警示，而非直接说明所有现代小说模型都具有相同比例的错误。[S08]

### 3.3 解决方案：带证据的双时间状态库

推荐最小结构：

```json
{
  "fact_id": "fact_0086",
  "entity_id": "character_01",
  "predicate": "left_arm_status",
  "value": "lost",
  "world_time_from": "day_16",
  "world_time_to": null,
  "narrated_in_chapter": "chapter_086",
  "epistemic_type": "objective_fact",
  "known_by": ["character_01", "character_07"],
  "source_span": "chapter_086:para_140-143",
  "status": "approved",
  "supersedes": "fact_0031"
}
```

**实现原则：**
1. `canon`（作者确认的客观事实）与 `belief`（角色相信之事）分开存储。
2. 保留世界发生时间与读者获知时间，避免倒叙/悬疑认知错位。
3. 所有状态变更必须有原文证据片段及版本号。
4. 草稿阶段的模型提取仅为候选状态，不自动污染正式设定。
5. 冲突时优先查看事件历史和人工签核，而不是覆盖旧记录。
6. 召回使用结构化查询、关键词检索与语义检索混合，并评估误召回。

ConWriter 的场景级写作、动态记忆、符号状态验证和局部修复，为这种控制策略提供了研究依据；Topo-Narrator 把人物图、剧情链和环境树分开，也说明“一个大摘要”不是唯一合理表示方式。[S09][S10]

### 3.4 可执行验收

- **关键事实冲突率**：抽查确认的严重矛盾数 / 每 1 万字，保留置信区间。
- **约束召回率**：写章节前，应召回的关键历史事实中被召回的比例。
- **事实污染率**：未经人工确认而被写入 canon 的错误事实占比。
- **误报率**：对合理误导、撒谎、魔法规则例外误判为硬冲突的比例。
- **回滚正确率**：章节撤回后，状态视图能否恢复到撤回前。

## 4. 技术根因二：局部连贯不等于整体叙事成功

### 4.1 三类失效

**（a）无目标的场景堆砌。**一个又一个场景看似有冲突，但对人物命运和核心主题没有净增量。  
**（b）节奏曲线机械化。**每章结尾都悬念，但缺少铺垫、缓冲与代价，读者很快习惯这种刺激。  
**（c）角色成长伪进化。**人物只是在能力、装备或地位上变强，却没有发生价值观与选择机制的变化。

LitVISTA 发现，模型在叙事事件锚点、功能与结构整体把握方面仍存在系统性困难，即便增强推理也不是稳定有效的万能方案。[S03]

### 4.2 解决方案：从故事承诺倒推场景

每个场景采用 `GOAL → OBSTACLE → CHOICE → CONSEQUENCE → STATE DELTA`：

| 字段 | 核查问题 |
|---|---|
| Goal | 此场景谁想要什么，为什么此刻必须要？ |
| Obstacle | 冲突是来自对手、世界规则还是角色内在弱点？ |
| Choice | 角色做出哪个具体、不可替代的选择？ |
| Consequence | 选择带来什么真实代价、反作用或信息变化？ |
| State Delta | 人物关系、信息、资源或能力有哪些持续变化？ |

每一卷应明确“阶段性失败/成功、价值观变化、主要关系变化、高潮代价、伏笔推进”；而不是只设定章节数与字数。

### 4.3 编辑层面的结构审查

- 先审 **全书冲突和人物弧线**，再审卷纲与章节，最后审句子；避免局部润色掩盖结构失败。
- 建立事件因果图：每个重大转折都应能追溯必要前置事件；允许巧合，但不能反复用巧合解决核心冲突。
- 设“无功能场景”诊断：如果移除某场景对人物、因果、信息、主题均无影响，则标记人工复审。
- 对连载题材评估读者的“继续阅读理由”，但不要把所有文学形式简化为爽点计数器。

## 5. 创造性与文学质量：为什么 AI 味会变成生产瓶颈

### 5.1 证据比常见口号复杂

2025 年 PNAS 论文 *Echoes in AI* 对短故事进行比较，发现模型多次生成会重复部分情节元素，且跨模型亦有相似组合；该研究说明“情节多样性风险”，但**不能直接证明每部 AI 小说均缺乏原创性或构成法律抄袭**。[S06]

2026 年 *Nature Human Behaviour* 研究汇总多个数据集与场景发现，大模型润色/改写和语言多样性下降有关。这是跨领域文本研究，可作为小说风格同质化的警示，但不应把它的具体数值直接外推到小说。[S07]

读者研究并非一边倒：有研究发现，AI 故事在短文本盲评里不一定比真人差，但标注“AI 所作”可能影响评价；另一项研究发现，部分读者的“进入故事世界”感更弱。不同样本、提示、体裁、标签条件会导致相反结论。[S21][S22]

### 5.2 症状与根因对照

| 症状 | 可能根因 | 不宜采用的伪解决方案 | 更可靠做法 |
|---|---|---|---|
| 全文充满抽象感悟 | 没有明确行动与选择 | ‘减少 AI 味’万能提示词 | 用具体行为承载情绪 |
| 对白所有人同声 | 角色声音未结构化 | 随机插入口头禅 | 角色语用目标/教育背景/禁用表达 |
| 冲突过于方便 | 大纲没有预先设定代价 | 要求“更曲折” | 限制角色资源与可用路径 |
| 每个高潮同一套路 | 只对即时刺激优化 | 每章随机反转 | 维护卷级情绪曲线和后果 |
| 原创性不足 | 生成候选空间过窄 | 同义词替换、洗稿 | 跨题材因果重组、作者原创事实输入、盲评 |

### 5.3 关键决策

**AI 负责候选结构、错误定位和表达建议，作者保留决定作品独特性的核心判断。**对于文学性较强的作品，允许使用“AI 只提问/诊断，不改写正文”的工作模式。

## 6. 质量评测的三层陷阱

### 6.1 自动裁判不是“客观真理”

LitBench 含 43,827 对训练比较与 2,480 对测试比较，其结果显示：当时最强现成评委模型的判断与人类偏好约 73% 一致，专训评判模型提升至约 78%。注意：这是该基准及模型条件下的结果，不是全部小说评价的通用准确率。[S05]

面向中文整本小说的 ChangJuan 整理了 300 部小说及人类评分、读者评价，提出面向长书的分维度评估方法；其论文报告相关性从 Kendall τ = 0.248 提升到 0.341，说明长书评价存在很大的改进空间。[S04]

### 6.2 必须分离的审查层

1. **机器硬约束层：**人物生死、位置、库存、时间、公开设定的规则；要求有证据。
2. **文本编辑层：**重复、冗余、对白不自然、视角跳变、信息交代失衡；多数仅能提出建议。
3. **文学与读者层：**人物吸引力、代入感、出人意料但合理的情节、主题和风格；必须引入人类判断与真实阅读实验。

不要将所有层级压成一个“AI 小说综合得分”。硬约束失败具有发布阻断权；文学评价则应允许分歧。

### 6.3 评委治理

- 自动评委对事实类问题必须输出`claim + contradicting_span + supporting_span + rule_id`。
- 不允许让生成模型对自身章节的主观好坏直接做唯一裁判。
- 评估提示词、温度、模型版本及样本顺序必须记录，避免结果漂移。
- 对风格、情绪和原创性使用至少两名真人盲评，记录评价者之间的一致性。
- 提供复核队列：评委意见相互矛盾、证据不足或存在叙事性误导时转人工。

## 7. 人机协作与 Agent 工作流的隐性成本

### 7.1 生产线最危险的失败形式

`写作 Agent`生成错误人物状态 → `摘要 Agent`错误概括 → `Memory Agent`将其当成正史 → `下一章节 Agent`基于错设定扩展 → `Editor Agent`只看局部文本继续润色。

这是一种**状态污染级联**：多 Agent 并不天然更可靠，有时反而为错误提供了多轮确认的错觉。[S09][S10]

### 7.2 推荐的治理闭环

```text
作者批准 Story Bible
       ↓
Planner 创建章节契约
       ↓
Retriever 组装证据与状态
       ↓
Writer 按场景生产候选文本
       ↓
Extractor 生成候选状态变化
       ↓
Verifier 核验硬约束与引用证据
       ├─ 失败 → 局部重写 → 重新验证
       ↓
Editor 评估叙事与风格
       ↓
作者批准章稿及状态变更
       ↓
提交不可变章节版本 / 更新正式事实视图
```

必须具有：事务性提交、幂等任务、模型调用日志、改稿差异比较、失败重试上限、状态回滚和人工最后裁决权。

### 7.3 人工负担是否真正降低？

对一个 5 万字测试故事，建议追踪：起草人工分钟数、核查分钟数、修订分钟数、事实维护分钟数、反复生成分钟数、最终作者接受率。若 AI 缩短草稿时间但大幅增加核查工作，实际效率可能并未提高。

## 8. 原创性、AI 洗稿与法律/平台风险

### 8.1 最需要区别的三件事

- **模型生成的常见套路相似：**可能是类型惯例，不自动构成版权侵权。
- **对他人具体表达的实质性挪用：**可能涉及著作权争议，需要结合具体权利、事实和法域判断。
- **无法证明人类创作贡献：**可能影响部分法域下的版权登记或权利主张。

2026 年中国作家网转引的网文产业调查描述了 AI 洗稿、人物关系与核心情节链条挪用、跨平台漫剧化的侵权争议及举证困难。这是已报道的案例，不代表所有 AI 创作流程都会侵权。[S13]

美国版权局 2025 年报告认为，AI 辅助作品可以获得版权保护，但仅靠提示词并不足以使纯 AI 输出自动满足人类作者贡献要求；具体权利认定必须按适用法律分析。[S16]

### 8.2 平台规则并不统一

- **中国标识制度：**《人工智能生成合成内容标识办法》自 2025-09-01 实施；用户在网络信息内容传播服务中发布生成合成内容，有相关声明和标识义务，具体适用须按角色及服务场景判断。[S14]
- **晋江：**其用户注册协议要求上传或发布人工智能生成合成内容时显著标识，平台可以采取检测与处置；其具体原创写作规范还需结合签约及公告核对。[S15][S13]
- **Amazon KDP：**正式规则明确区分 AI-generated 和 AI-assisted；AI 生成文本即使后来大量修改，仍可能属于需申报的 AI-generated，单纯辅助改稿的定义不同。[S17]

建议为每个平台建立 `policy_snapshot`（规则链接、抓取时间、适用作品形态、待人工确认事项），在每次发布前重新核验。

### 8.3 为什么不能依赖 AI 检测器定罪

AI 检测器根据文本统计特征推断，不是直接读取文本生产历史。2026 年关于检测器的研究与案例提醒，单个分数可能受文本风格、改写和样本影响；应保存草稿版本、编辑记录和人工创作说明，而非以单次检测作为高风险处置的唯一依据。[S20][S18]

**建议：**保留原始草稿、关键人工变更、模型调用范围、素材权利证明和成稿版本哈希；对侵权风险采取“人工复核 + 版权专业意见 + 证据保存”，不提供规避检测的洗稿流程。

## 9. 数据安全与生产可用性

稿件、未发布 IP 设定、商业计划、签约信息和作者隐私属于高敏感业务资产。系统应提供：租户隔离、最小权限、日志脱敏、加密存储、模型供应商留存策略核验、可配置的数据保留/删除、导出与撤销授权；引用第三方内容要有许可依据。面向公众提供生成式 AI 服务还可能涉及中国现行生成式 AI 服务规定。[S25]

**工程失败场景：**同一创作工作室的两个作者，其角色知识库检索结果串库。此类问题哪怕发生一次，也可能构成严重的商业信誉和保密事故。必须通过租户隔离测试，而不是靠提示词声称“不要泄露”。

| 方案/研究 | 已有解决思路 | 仍需核验的缺口 |

| ConWriter | 场景级生成、动态记忆、符号约束、局部修复 [S09] | 大规模长期连载、多作者协作和真实读者偏好 |

## 11. P0/P1/P2 解决方案路线图

### P0：可验证的生产闭环

**范围：**一个题材、一个主作者、一部 3–5 万字测试故事；先实现可用的事件日志、角色事实、章契约、人工审批、引用式矛盾检测与回滚。

**交付物：**`story.schema.json`、`character.schema.json`、`event.schema.json`、`chapter_contract.schema.json`、`continuity_rules.yaml`、可审查的章节与版本变更记录。

**退出条件（建议性目标，不是行业基准）：**关键事实的可追溯率 > 95%；所有发布章节有作者确认状态；零个未经确认的机器候选事实进入正式 canon；任何失败章节可回滚至前一批准版本。

### P1：叙事质量与成本优化

**范围：**伏笔 DAG、全书节奏仪表板、人物动机曲线、独立编辑 Agent、局部修订、检索质量测试和人工盲评。对照简单提示词基线量化收益。

**退出条件：**在相近预算和人工投入下，严重矛盾更少，盲评不显著劣于基线；若无改善，停止增加 Agent 数量并分析检索/评委误差。

### P2：多作品和发行生态

**范围：**多租户、团队协作、出版商权限、平台政策快照、发布前申报核查、合规留痕、有声书/翻译/剧本/分镜派生接口。

**退出条件：**作者愿意反复使用，作品按时完成，单位合格定稿成本可控，具备真实发行闭环及版权链条。

## 12. 建议执行的对照实验（研究而不是营销演示）

### 12.1 实验假设

- H1：结构化状态+证据检索，能够比“仅添加长摘要”更有效降低关键事实矛盾。
- H2：场景契约+卷级规划，能够改善全书叙事连贯性，但未必提高独创性。
- H3：自动评委的事实错误检测能力高于其评估文学吸引力的可靠性。
- H4：随着章节增加，未经验证的状态污染将显著增加编辑返工。
- H5：增加 Agent 不必然提高单位合格定稿效率。

### 12.2 四组系统对照

| 实验组 | 方法 | 用来回答的问题 |
|---|---|---|
| A | 直接 Prompt + 最近章节 | 单模型起点表现 |
| B | 全书大纲 + 定期摘要 + RAG | 常见工程方案是否足够 |
| C | B + 状态机 + 时间线 + 引用式检查 | 结构化一致性治理收益 |
| D | C + 分层编辑 + 人工审核闸门 | 完整协同流程净收益 |

建议先运行小规模 pilot：2 类题材 × 2 个长度档 × 2 个随机种子 × 4 组 = 32 部测试文本。长度档和读者工作量可根据预算确定。确保四组拥有同类选题、相近预算、同一评价规则，并随机化作品顺序。

### 12.3 核心指标定义

| 指标 | 定义 / 注意事项 |
|---|---|
| Hard Contradictions / 10k | 每 1 万汉字的人工复核严重硬矛盾数量 |
| Evidence-grounded Precision | 自动标注矛盾中经人工确认的比例 |
| Evidence-grounded Recall | 预先植入矛盾集合中被正确找出的比例 |
| State Drift | 当前事实与原 canon 不一致但未经批准的状态数量 |
| Arc Quality | 人类读者盲评情节因果、高潮铺垫与收束；分维度量表 |
| Voice Distinctiveness | 混合台词中识别不同角色声音的正确率（作为代理指标） |
| Edit Minutes / Accepted 10k | 每万字合格定稿所需人类编辑时间 |
| Net Cost / Accepted 10k | API、基础设施、人力及重试费用除以验收字数 |
| Reader Continuation Intent | 看完节选后愿意继续阅读的比例（不等于真实付费） |
| Platform Compliance Pass | 每个平台发布前应披露/授权/审核项完成比例 |

**因果识别注意：**同一题材中不同故事本身的吸引力差异很大；使用匹配创意简报、足够多随机种子、盲评与置信区间，避免用一部优秀作品作“全面领先”的证据。

## 13. 推荐的系统架构与数据结构

```text
interfaces/
  author_studio/      # 作者工作台：审批、差异、故事地图
  editor_console/     # 编辑核查：证据、问题、分配
services/
  story_planner/      # 总纲、卷纲、章/场景契约
  story_writer/       # 模型适配、场景候选与重写
  state_extractor/    # 事件/状态候选抽取
  story_memory/       # canon/belief/rumor/time/knowledge
  continuity_checker/ # 规则引擎、检索证据、冲突定位
  literary_editor/    # 分层评审、风格评测、建议
  policy_guard/       # 平台规则、版权与披露清单
  experiment_lab/     # 基线、盲评、统计与回归
storage/
  manuscripts/        # 版本化正文
  evidence_spans/     # 证据片段、版本哈希
  story_events/       # 不可变事件日志
  state_views/        # 按角色和时间聚合的状态视图
  publication_logs/   # 发布审定与平台政策版本
```

### 13.1 数据模型中的关键字段

- `source_span`, `source_hash`: 事实和审校结论能定位到哪一版的哪一段。
- `world_valid_from/to`: 事实在故事世界生效的时间区间。
- `narrative_revealed_at`: 读者在何处被告知。
- `known_by`, `belief_holder`: 角色认知权限与误解来源。
- `canon_status`: candidate / reviewed / approved / superseded。
- `agent_run_id`, `model_version`, `prompt_version`: 可审计的生产溯源。
- `editor_decision`, `reason`: 人类决定与原因。
- `rights_basis`, `distribution_policy_version`: 素材权利基础和发行规则快照。

### 13.2 质量门禁

```text
DRAFT -> STRUCTURAL_REVIEW -> CONTINUITY_REVIEW
      -> EDITOR_REVIEW -> AUTHOR_APPROVAL
      -> CANON_COMMIT -> DISTRIBUTION_CHECK -> PUBLISHED
```

**规则：**机器可以提出候选事实和问题，但不能越权将其视为作者定稿。审校失败默认产生局部修复任务，超过重试预算即转人工。严禁为通过审校而改写既定剧情事实。

## 14. 商业化判断：优先做哪种产品

**第一选择：小说一致性审校与记忆工具。**面向已拥有正文的作者，支持导入、角色/事件抽取、跨章矛盾定位、引用式修改建议与人工确认。其价值可直接通过节省编辑时间与错漏下降验证。

**第二选择：中文长篇编辑工作台。**融合卷级结构诊断、角色弧线、伏笔图谱、风格对比和真实读者测试；在工具侧保留作者表达，而不是追求代笔率。

**第三选择：从小说到 IP 衍生的资产中台。**长期价值较大，但必须建立授权链、视觉与剧情统一资产，且面临更多平台和合作方依赖。

**不建议作为起点：**以“几分钟自动写百万字”为主卖点的无人工验收平台。这可能带来短期演示效果，但难以证明真实阅读价值、改稿效率与可持续发行能力。

## 15. 待进一步调查的问题与数据缺口

1. 中文 30 万字以上的 AI 协同创作，有没有公开、统一、可复现实验数据？目前证据明显不如英文短篇和一般文本任务充分。
2. 不同细分题材（玄幻、悬疑、言情、历史、科幻）的一致性错误和读者偏好是否不同？
3. “先生成后检查”与“生成时执行约束”谁更经济？应在相同预算下比较。
4. 人工编辑环节究竟节省还是转移了劳动？需要真实使用日志而非访谈回忆。
5. 机器评审能否提升真实平台的读者追更和付费？不能用模型分数替代经营结果。
6. 创作过程证据如何以尽量低成本同时服务版权申报、合规与纠纷举证？
7. 多媒体衍生时，故事资产对漫画/短剧创作效率的提升能否达到可出售的水平？

# 第二部分：20 类 Issues 的现有解决方案与工程实施手册（2026-11-17 增补版）

> **增补说明：**本部分对前文 I01—I20 逐项给出“现有方法 → 解决机制 → 实施步骤 → 适用边界 → 可测试指标”。论文结论仅在原实验范围内有效；产品文档证明功能存在，不证明该功能已在中文百万字长篇达到特定准确率；本文提出的组合架构均标记为**工程建议/待验证**。

## 16. 总体技术决策：不要选择单一万能方案

目前存在四条互补路线：（A）**规划驱动**：StoryWriter 的事件纲要—章节计划—正文生成；（B）**状态约束**：ConWriter 的动态记忆、状态迁移校验和风险驱动局部修复；（C）**异构记忆**：Topo-Narrator 的人物图、情节链、环境树；（D）**可追溯审校**：ConStory-Checker 的矛盾定位和文本证据。对于写作工作台，Novelcrafter Codex 支持名称/别名追踪和按条件注入设定，Sudowrite Story Bible 提供简介—角色—大纲—场景的组织能力。[S02][S09][S10][S11][S12][S26][S39][S40]

**不能误判：**上述技术没有一个单独证明能够以低人工投入稳定生产商业可发行的百万字中文长篇小说。推荐以“作者掌控的规划、可靠的状态记录、证据式审稿、局部修复和人工审批”组合试验，最终以盲评和净编辑工时衡量，而非单看生成长度。

| 方法 | 已有代表方案 | 对应问题 | 成本和约束 | 工程判断 |
|---|---|---|---|---|
| 长上下文 + 摘要 | 常规 LLM 写作、StoryWriter 历史压缩 | I03/I07 | 低门槛，但摘要漂移、上下文位置影响 | 只作基线，不作唯一记忆 |
| 人物/世界观百科 | Novelcrafter Codex、Sudowrite Story Bible | I01/I04/I14 | 作者需维护条目，知识更新不自动可靠 | 很适合作者工作台 |
| 结构化情节/状态 | ConWriter、Topo-Narrator | I01/I02/I08/I09 | 数据模型和迁移设计复杂 | 核心工程投资方向 |
| 混合检索与过滤 | OpenSearch/Weaviate | I07/I13/I19 | 要维护索引、权限和回归集 | 必须先做过滤再排序 |
| 人机审批的有状态 Agent | LangGraph、Temporal | I11/I12/I14/I18 | 编排更可靠，但不自动提升文采 | 适合生产部署 |
| 分层评价/真人盲评 | LongStoryEval、ChangJuan、LitBench | I03—I06/I10 | 评测标注开销较高 | 分离硬约束和审美 |

## 17. 逐项解决方案：I01—I20

### I01｜人物、物品、地点与事实前后冲突（P0）

**可观察失效：**角色已失去某件装备，却在下一卷再次使用；地点距离、人物年龄或伤势改变却没有合法事件。**已有方案：**ConStory-Bench/ConStory-Checker 提供矛盾分类和证据定位；ConWriter 在场景生成中加入状态迁移约束；Novelcrafter Codex 的条目、别名与出现追踪帮助作者查看设定。[S02][S09][S11]

**推荐落地：**将“角色状态表 + 事件日志 + 条目来源”独立于正文维护。定义 `character_id/entity_id/attribute/value/valid_from/valid_to/source_span/status`；章节起草前读取当前批准状态，生成后提取候选状态变化；不可直接更新 canon。对装备持有、生死、伤势等建立确定性规则，对暗示性描写使用带引用的 LLM 检查。采用 append-only 事件日志，批准后产生新状态快照。

**约束与失败模式：**象征性、梦境、伪装、超自然例外可能触发误报；仅靠正则识别人物名会漏掉代称。**验收：**人工植入的状态矛盾召回率、误报率、原文证据定位正确率、未经批准状态写入次数；任何误报均保留人工驳回机制。

### I02｜时间线、因果与角色知识边界错误（P0）

**可观察失效：**角色在知道秘密之前说出秘密；闪回发生顺序错误；角色在同一时刻出现于两个无法抵达的位置。**已有方案：**ConStory-Bench 的时间情节类错误体系与 Topo-Narrator 的事件链，提供可参考的任务结构；其余强校验属于需要自行实现的工程层。[S02][S10]

**推荐落地：**维护两种时间：`world_time`（故事内发生）、`narrative_time`（读者看到），外加 `known_by`、`disclosed_at`、`belief/rumor/canon`。以 `precedes / causes / reveals / located_at` 建立有向约束图；在分章发布前执行无环检查、行程可达性校验和信息知悉边界检查。回忆与不可靠叙述要标注“叙述视角”，不能直接当作世界事实。

**约束与失败模式：**模糊年代、时差、修辞性倒叙难以自动规范；系统要允许显式“不确定”。**验收：**在人工注入的 30—50 个时间/知识错误测试中分项统计 Precision/Recall；检查器必须输出 `冲突事实A + 冲突事实B + 生效时间 + 两处证据`。

### I03｜大纲偏航、节奏失衡、虎头蛇尾（P0）

**可观察失效：**单章读起来通顺，但卷级高潮缺乏铺垫，副线膨胀，结尾突然收束。**已有方案：**StoryWriter 将事件型大纲、章节规划和正文生成拆成 Agent；Sudowrite Story Bible 可维护并生成大纲；LitVISTA 提供叙事功能与全局结构诊断的研究框架。[S03][S12][S26][S40]

**推荐落地：**全书采用三层契约：`book_promise`（主题/结局承诺）、`arc_contract`（阶段目标/转折/代价/收束）、`chapter_contract`（本章状态变化/必须推进的关系/悬念）。每 5—10 章执行卷级重规划：对比“预定事件图”和“已批准事件图”，标出漂移原因，由作者选择接受偏航还是修改后续章纲。绘制事件密度、冲突强度、反转与兑现点的可审查时间图。

**约束与失败模式：**指标化节奏不等于文学优劣；刻意缓慢、实验性结构不应被自动判错。**验收：**人工编辑评价全局连贯性、收束完整性；与无卷纲基线做成对盲评，报告置信区间。

### I04｜人物成长、动机与关系机械化（P0）

**可观察失效：**人物的价值观或关系突然转变，配角沦为功能性工具，同一人物每次都用相同方式解决问题。**已有方案：**Novelcrafter 支持人物条目及关联资料；StoryWriter 的事件/人物关系组织有助于在计划阶段显式追踪人物；LitVISTA 可用于检查事件的叙事功能，但不等于已解决角色成长生成。[S11][S26][S03]

**推荐落地：**每名核心人物维护 `desire（想要）/need（真正需要）/fear（恐惧）/misbelief（错误信念）/relationship_state（关系）/turning_points`；每卷至少审查一次“人物选择—代价—信念变化”因果链。对关系增加方向性和事件证据（A 信任 B 不等于 B 信任 A）；场景契约要求重大选择与此前动机相容，若相悖需标记可解释转折。

**约束与失败模式：**角色的反常、伪装、精神崩溃可能恰恰是戏剧目的。**验收：**人工能够从关键选择追溯前因的比例、对白角色辨识度、人物弧线盲评；禁止将性格量表当作创作唯一标准。

### I05｜情节同质化与原创性不足（P0）

**可观察失效：**不同作品反复出现相似反派、升级套路和转折链，即使语言已换词。**已有证据与方法：**PNAS 2025《Echoes in AI》对短篇故事的重复情节组合做量化；2026 年创造力研究提出新颖性、价值、要求遵循、共鸣等分维度评价。[S06][S33]

**推荐落地：**选题阶段先由作者提供不可替代的独特世界事实/伦理矛盾，再独立生成 6—10 组“因果机制不同”的候选大纲；对候选做事件三元组和关键转折嵌入聚类，删去高度同构的情节路线；保留被拒方案与原因。将新颖性与合理性、情感效果分开评估，采用真人读者盲评，而非以高温采样或同义词替换冒充创新。

**约束与失败模式：**题材惯例不等于抄袭；文本相似性也不能独立作侵权判断。**验收：**候选故事事件结构多样性、盲评意外感与合理性双评分；避免把意外程度最大化导致情节失真。

### I06｜文字“AI 腔”、对白同质、过度解释（P1）

**可观察失效：**大量抽象感悟、无用修饰、人物说话口吻趋同、句式过分均匀。**已有方案：**Sudowrite 提供改写、扩写与反馈功能；2026 年语言多样性研究提醒 AI 改写可能让文本表达趋同；创作评价研究指出风格与情绪共鸣不宜仅靠单模型判断。[S07][S12][S33]

**推荐落地：**建立作者提供的 2—5 段合法样文作为 `voice_reference`，记录叙述视角、句长倾向、叙述与对白比例、禁止的表达习惯；角色分别建立口语动机、知识背景与言语禁区。按“诊断 → 给出例句与原因 → 人工选择 → 局部改写”执行。使用具体动作/后果替代情绪标签；对重写前后做差异高亮。

**约束与失败模式：**自动“去 AI 味”可能伤害作者风格；不能以通过检测器为目标。**验收：**风格保真盲评、不同角色混合对白辨识率、每万字无功能说明性句子的人工标注趋势。

### I07｜旧信息召回失败、检索噪声与上下文污染（P0）

**可观察失效：**相关人物的关键伤势没有被检索，反而注入大量无关历史背景；相似名字造成串人。**已有方案：**OpenSearch/Weaviate 的混合检索把 BM25 与语义向量相结合，可配合字段过滤和重排；Novelcrafter 对条目注入时机有明确配置。[S29][S39]

**推荐落地：**执行分级召回：先通过作品/分支/版本/实体 ID 和有效时间做**强过滤**；再用关键词 + 向量并行召回；融合排序后对候选证据做重排；最终按 `required_canon > active_arc > recent_scenes > optional_style` 分配 token 预算。建立按章节的检索黄金集合，测量必须事实是否命中，并记录未注入的原因。

**约束与失败模式：**向量检索找不到不存在于候选集中的信息；重排无法弥补前级漏召回。**验收：**Recall@k、Precision@k、有效 token 比例、注入成本与误关联率；每次模型输出都记录注入证据 ID。

### I08｜摘要漂移与角色误解污染“正史”（P0）

**可观察失效：**摘要把“他猜测父亲已死”写成“父亲死亡”；后续 Agent 继承错误。**已有方案：**ConWriter 的动态记忆及符号状态控制提示了结构化状态的必要性；Topo-Narrator 对人物、情节与环境采用异构表示，可降低将所有信息混入一条摘要的风险，但不直接保证事实抽取准确。[S09][S10]

**推荐落地：**对抽取结果强制输出 `subject/predicate/object/epistemic_type/source_span/confidence/canon_status`，其中 `epistemic_type` 必须区分客观事实、主观信念、传闻、意图、反事实、梦境。摘要只是检索加速层，不具有修改世界事实的权限；每个候选变更需通过实体消歧、证据校对、冲突检测及作者批准。状态更新使用 `expected_version` 比对，避免并发覆盖。

**约束与失败模式：**隐喻、反讽、故意误导使“真相”可能暂不可定。**验收：**事实抽取精确率、事实污染率、来源可追溯率、冲突版本检测率；关键错误以人工样本判定。

### I09｜伏笔种植、延迟披露与回收失败（P1）

**可观察失效：**重要悬念被遗忘；过早揭谜；回收没有必要前置条件。**已有方法：**StoryWriter 的事件关系图、Topo-Narrator 的剧情链适合作为依赖组织的研究参考；具体伏笔回收追踪需要业务侧自行实现。[S26][S10]

**推荐落地：**为伏笔维护 `clue_id/plant_chapter/reader_knowledge/character_knowledge/payoff_candidates/deadline/status`；引入 `requires/reveals/pays_off/contradicts` 关系，形成伏笔 DAG。章规划时检索“本卷应推进但尚未推进”的伏笔。回收不自动定性为完成，而由作者确认是否真正解释了前文信息。

**约束与失败模式：**文学上允许开放结局或永不揭示；不应强制 100% 回收。**验收：**关键伏笔履约率、计划外提前揭示次数、回收时读者理解度与惊喜度。

### I10｜自动编辑裁判不可靠（P0）

**可观察失效：**模型对自己的作品打高分，对风格或类型偏好明显；分数随机波动。**已有方案：**LitBench 使用成对的人类偏好数据校验自动评委；ChangJuan 对中文整本故事采用长短均衡摘要、代表性片段、维度评价与题材权重；LongStoryEval 对整本小说比较汇总式、递增式与摘要式评价；2026 创造力研究证明不同评分机制之间仍有结构差异。[S04][S05][S27][S33]

**推荐落地：**将评估分为三层：①确定性规则和证据矛盾，作为硬门禁；②语言与结构缺陷，提供带引用的问题建议；③整体吸引力与审美，必须采集多个真人盲评分。对 LLM 裁判采用成对 A/B 盲判、顺序对调、独立模型和标注协议；记录评委模型版本、Prompt 版本、题材。不同目标分别训练或校准，不求单一“质量总分”。

**约束与失败模式：**研究基准的 73% 或 Kendall τ 不能拿来作为本系统的实测结果。**验收：**人工一致性、A/B 顺序偏差、分题材相关性、事实检测 F1、不同版本评委排名稳定性。

### I11｜自动重写引入新问题、审稿无限循环（P1）

**可观察失效：**改一句伤势设定，连带改变角色关系；编辑 Agent 连续五轮提出相互矛盾的修改。**已有方案：**ConWriter 采用风险提示与局部修复；LangGraph/Temporal 提供可持久化的任务状态与受控重试机制，属于工作流可靠性，不是文学质量自动保证。[S09][S30][S31]

**推荐落地：**以 `edit_patch` 为修复单位：存储 `span_id/before_hash/after_text/issue_id/expected_state_delta`，只允许修改目标片段及明确依赖范围；Patch 前后重新执行受影响事实/章节测试。限制每个 issue 的最大修复轮次与 token 预算，失败则转人工。禁止通过篡改 canon 来让检测通过。

**约束与失败模式：**有时真正的问题在大纲上，局部修补不可解决，必须升级到卷级结构审查。**验收：**一次修改引入的新严重错误数、净修复成功率、每处问题平均编辑分钟数、循环超预算比例。

### I12｜多 Agent 协作状态竞争与不可恢复任务（P1）

**可观察失效：**规划 Agent 和写作 Agent 使用不同版本的设定；任务重复执行生成两个正式章节。**已有方案：**LangGraph 提供 checkpoint、interrupt 和人工恢复；Temporal 提供持久执行、Activity 重试、幂等实践及 Saga 补偿。[S30][S31]

**推荐落地：**所有 Agent 读同一个批准版本快照，任务状态采用 `PLANNED→DRAFTED→CHECKED→APPROVED→COMMITTED`；提交时执行 `compare-and-swap(expected_version)`；任务以 `work_id + chapter_id + revision` 作为幂等键。将模型输出标记为“候选”，只有 `CanonCommit` 服务能写正式故事状态。对发布等外部副作用采用事务外盒（outbox）与幂等提交。

**约束与失败模式：**工作流引擎无法替代数据库事务；并行写作仍需显式依赖管理。**验收：**断网/进程崩溃恢复测试、重复提交零副作用、并发改稿冲突准确拒绝、审批审计完整性。

### I13｜专业知识、历史与真实世界细节失真（P1）

**可观察失效：**历史纪年不符、医学或法律程序错误、地理行程不合理。**已有方案：**检索增强生成（RAG）与混合检索可辅助找到权威资料；结构化引用和专家复核属于应用层控制。[S29]

**推荐落地：**区分 `fiction_canon`（作者设定可虚构）与 `external_fact`（需要可核验的现实知识），为外部事实建立可信资料来源、时间戳、法域、授权与证据片段。敏感专业场景优先调用有出处的检索，输出 `claim/source/date/jurisdiction/uncertainty`，历史文学允许明确标识的架空设定。重要医疗、法律、科学叙述应由领域专家审核，不把模型回答视为权威。

**约束与失败模式：**资料本身可能过时、相互冲突，检索不等于事实正确；创作不需要每个细节都教科书化。**验收：**可核验事实的来源覆盖率、独立专家事实错误率、引用失效率。

### I14｜作者控制权下降、工作量被转移（P1）

**可观察失效：**草稿生成更快，但人工要检查大量冗长建议；作者越来越难把握自己的故事。**已有方案：**Novelcrafter 的资料注入和作者控制选项、Sudowrite 的大纲/手工编辑支持“协同创作”模式；LangGraph 的人工中断能够建立审批节点。[S11][S12][S30]

**推荐落地：**提供三种清晰模式：`suggest_only（只诊断）`、`co_write（局部共写）`、`autodraft_with_approval（自动草稿待批）`；重要情节/世界事实/正式发布必须由作者明确签核。UI 使用差异对比、引用证据、建议理由与一键驳回，按缺陷严重度排序，避免编辑噪声。导入既有作品时保留原有章节版本和署名。

**约束与失败模式：**“更多自动化”不必然减少作者劳动；不同作者偏好差异大。**验收：**每万字合格定稿人类总工时、作者接受率、非请求改写比例、问卷中的控制感与满意度。

### I15｜AI 洗稿、实质性相似与权属链不清（P0）

**可观察失效：**只修改表面措辞却继承他人的表达、人物组合与关键情节安排；素材授权证明丢失。**现有制度依据：**美国版权局 2025 年报告阐释人类表达性贡献与版权保护的关系；相关中文平台及国家规则需要按法域和业务场景区分。[S16][S13][S14]

**推荐落地：**为每个外部素材维护 `source_uri/author/rights_basis/licence/allowed_uses/accessed_at`；生成链记录人工主导的关键叙事决策和历次编辑差异。原创性审查采用多层“字符串近似→语义疑点→人物关系/关键事件对照→版权专业人员复核”，不把通用题材元素自动判侵权。优先使用作者原创设定和合法授权文本，而非输入在版权范围不明的整本竞品进行仿写。

**约束与失败模式：**相似度算法无法完成法律意义上的实质性相似判断，著作权保护和平台合同也可能不同。**验收：**权利资料完整率、重大疑点人工复核率、最终发布版权链可导出性；不设“相似度低就安全”的伪阈值。

### I16｜AI 文本检测误报与错误处罚（P0）

**可观察失效：**同一篇真人文章经润色后被误判 AI 所写，不同检测器互相矛盾。**已有研究：**2026 年关于文本检测的评述与实测发现明显不一致与误报风险；这些研究主要针对学术写作，并非直接测量中文小说平台。[S20][S36]

**推荐落地：**以“过程证据优先”取代“检测分数定罪”：留存原始草稿、作者修改、版本 diff、模型调用范围、生成内容声明、签名哈希及时间戳。检测工具只作为低权重线索；任何影响账户、版权或收入的处罚必须有独立证据、复核与申诉通道。准确区分“AI 辅助编辑”和“AI 实际生成文字”的平台定义。

**约束与失败模式：**过程日志证明系统内的操作历史，不自动证明外部不存在另一种创作过程。**验收：**误报申诉可恢复率、审计记录完整率、审核结论可解释性；不得以规避检测为优化目标。

### I17｜平台规则、标识、签约与上架限制（P0）

**可观察失效：**同一作品在一个平台可发布，在另一个平台需要声明、修改或受限。**已确认规则：**中国《人工智能生成合成内容标识办法》规定适用服务的标识要求；Amazon KDP 明确区分 AI-generated 与 AI-assisted，且生成文本经大幅修改仍可能属于需要申报的类别。[S14][S17][S34]

**推荐落地：**以 `distribution_platform + content_type + region + policy_version` 建立规则快照，发布前检查：是否允许此类 AI 参与、是否需要显式/隐式标识、作品与素材权属、签约声明、年龄与内容限制、发布格式。每次上架前重新核验官方页面，并由责任人做最终判断；不要在 Prompt 中硬编码永久不变的“政策答案”。对中国不同平台另设专项人工核验工作表。

**约束与失败模式：**站外媒体报道不能替代签约合同；标识义务的适用主体和具体场景存在差异。**验收：**需披露项目漏项数、上架退回原因、规则快照新鲜度、发布证据可追溯率。

### I18｜模型开销、延迟、重试与单位成本失控（P1）

**可观察失效：**每章重复送入整部小说，多个 Agent 对同一内容反复评价，失败重试造成高额账单。**已有技术：**部分模型服务提供上下文缓存；LangGraph/Temporal 的持久化任务与有界重试可避免任务从头重复，具体价格收益取决于供应商和缓存命中。[S30][S31][S38]

**推荐落地：**按任务难度路由：事实抽取/格式检查优先廉价模型或规则，复杂情节与文学编辑使用更强模型；固定设定前缀尽量缓存，状态变化部分动态注入；严格记录每一步 input/output tokens、缓存命中、重试、延迟、人工分钟数。设 `budget_per_chapter`、`max_revisions`、`max_context_tokens` 和低置信度升级策略。失败恢复时使用持久化结果，外部调用增加幂等防重。

**约束与失败模式：**较便宜模型可能增加错误与返工；缓存可能缓存过期版本。**验收：**`(API + 算力 + 人工 + 重试)/合格定稿万字`、P95 章节交付延迟、缓存失效率、预算超支比例。成本优化必须保持质量非劣性。

### I19｜稿件隐私、跨租户检索与外部数据泄露（P0）

**可观察失效：**工作室 A 的未发布设定被工作室 B 检索，模型日志记录用户私密稿件，未授权外发。**已有行业指导：**OWASP LLM 2025 风险指南单列敏感信息披露以及向量和嵌入系统弱点，明确提示跨租户泄露与检索投毒风险。[S32][S37]

**推荐落地：**数据写入与检索均强制 `tenant_id/work_id/acl` 服务端过滤，禁止只让模型在文本中遵守权限；密钥管理、传输与静态加密、日志脱敏、数据最小化、备份隔离和可配置删除。外部模型供应商逐项审核训练使用、保留期、地域与合同。针对上传的第三方文档实行不可信输入隔离，防 Prompt Injection。设置 Canary 测试：A 租户的独特标记词在 B 账户任何检索/生成路径都不得出现。

**约束与失败模式：**向量索引隔离、缓存隔离、备份与监控日志都必须覆盖；单靠“本地部署”也不自动安全。**验收：**跨租户泄露测试为零、越权拒绝率、敏感日志暴露审计、删除与备份清理验证。

### I20｜读者留存、收入与 IP 转化无法闭环（P1）

**可观察失效：**可无限生成内容却没人读完、愿意订阅或购买；改编脚本与人物设定脱节。**已有研究/方法：**LongStoryEval、ChangJuan 采用读者评论与评价维度作为质量信号；跨媒体的 DramaAgent 研究使用持久人物状态与目标化修复控制视听连贯性，但不能直接推定商业回报。[S27][S04][S41]

**推荐落地：**形成三层运营指标：①质量代理指标（严重矛盾、盲评）；②真实阅读指标（首章到第三章的继续阅读、章节追更、收藏、差评类型）；③经营指标（授权收入、平台净回款、人工制作和发行成本）。把读者反馈映射到后续章纲的建议单，已发布 canon 只有经作者批准才能更改。IP 衍生使用统一角色、剧情、授权和镜头资产 ID，保留每种媒介的艺术改编自主权。

**约束与失败模式：**平台算法、封面、流量入口会混淆内容质量与留存；不可将单次 A/B 结果视为因果结论。**验收：**相同题材/入口条件下的留存对照、净贡献毛利、IP 资产复用率、已发布剧情追溯完整率。

## 18. 技术实施蓝图：从可运行原型到可靠生产

### 18.1 数据域与不可逾越的权限边界

1. **Manuscript Store：**正文版本、段落稳定 ID、diff、作者审批记录；只读历史版本不可删除或静默覆写。
2. **Canon Service：**批准后的客观事实、规则、人物与物件状态；所有变更必须关联事件和来源证据。
3. **Belief Store：**按人物管理其相信/不相信/未知的事实，支持谎言与不可靠叙述。
4. **Timeline Service：**世界时间、叙述时间、事件前置条件和地理可达性。
5. **Retrieval Service：**权限过滤 + 关键词与语义混合检索 + 证据重排 + 预算分配。
6. **Quality Service：**强规则、证据式 LLM 诊断、文学编辑建议和真实读者标注相互分离。
7. **Policy & Rights Service：**版权素材授权、生成日志、目标平台政策快照和发布前审批。

### 18.2 提交协议：防止 Agent 污染故事状态

```text
1. Planner 输出 ChapterContract(expected_canon_version=N)
2. Retriever 获取版本 N 的 facts/beliefs/timeline + evidence IDs
3. Writer 产出 Draft(revision_id, source_context_hash)
4. Extractor 产出 CandidateStateDeltas（不写 canon）
5. Validator 执行规则检查、证据检查和冲突分类
6. Editor 给出文学建议和可定位 Patch
7. Author 批准正文版本和每条状态变更
8. CanonService 原子校验 expected_version=N，提交事件后变成 N+1
9. Indexer 按提交事件增量重建检索视图
10. Publisher 根据目标平台政策快照进行单独审批
```

**并发策略：**同一条主线默认章节串行提交；可并行生产候选章节，但同一时间只能有一个正式 canon 写入者。并行分支在合并前必须执行 rebase 式状态对照，避免以“最后写入覆盖前者”解决故事冲突。

### 18.3 建议的模块选择

| 模块 | 最小技术方案 | 升级条件 | 说明 |
|---|---|---|---|
| 主存储 | PostgreSQL，结构化表 + JSONB | 多作品高并发时再分片 | 版本与事务比数据库新颖性重要 |
| 搜索 | PostgreSQL FTS + pgvector | 召回/流量达到门槛再引入 OpenSearch | 对关键事实必须保留字段强过滤 |
| 流程 | 单体队列 + 状态机 | 跨数小时/长审批再引入 LangGraph/Temporal | 别以 Agent 数量充当完成度 |
| API | Python + FastAPI + Pydantic | 多工作室才做租户平台化 | 所有 LLM 响应都做 schema 校验 |
| 版本 | 章节快照 + 事件日志 + 内容哈希 | 需要协同编辑时加 CRDT/OT | 避免只用文件名表示版本 |
| 评价 | pytest fixture + 独立评审 + 人工标注 | 数据积累后校准 reward model | 先定义失败样本，再优化指标 |

## 19. 验收实验、失败注入与量化原则

### 19.1 四组对照：比“增加 Agent”更重要的是净收益

- **A 基线：**单模型 + 最近两章。
- **B 检索：**A + 章摘要 + 普通 RAG。
- **C 状态控制：**B + 时间化 canon/belief + 证据式验证。
- **D 完整流程：**C + 分层计划 + 局部修订 + 人工审批。

实验采用同题材/同创意简报、相近总预算、固定模型版本与盲评条件。重点观察 I01/I02 是否下降，以及 I03/I04/I05 是否真正改善；如果 D 只降低事实错误却降低文学吸引力，应如实报告权衡，不可只公布综合高分。

### 19.2 最小失败注入集（建议先做 12 类，每类 10—30 样本）

| 编号 | 注入类型 | 预期诊断 |
|---|---|---|
| F01 | 已死亡角色无复活原因再次出现 | 状态/世界规则冲突 |
| F02 | 未获知秘密的角色提前说出秘密 | 角色知识边界违背 |
| F03 | 倒叙场景被错误排序 | 世界时间 vs 叙述时间混淆 |
| F04 | 同义别名导致人物 A/B 合并 | 实体消歧错误 |
| F05 | “我以为他死了”被摘要记成死亡事实 | 信念污染 canon |
| F06 | 伏笔在回收前被另一章节提前揭示 | 披露时机错误 |
| F07 | 修复一个事实错误后引入关系冲突 | 重写回归失败 |
| F08 | 重试提交同一章节两次 | 幂等缺陷 |
| F09 | 两个 Agent 基于旧版本并发写 canon | 版本冲突应阻断 |
| F10 | 租户 B 查询到租户 A 的人物 | 越权泄露应阻断 |
| F11 | 检索到无权限的竞品全文 | 权限和授权过滤缺失 |
| F12 | 标识规则更新后沿用旧发布清单 | 平台合规快照过期 |

### 19.3 指标字典（先定义，再实验）

| 指标 | 公式/测法 | 注意点 |
|---|---|---|
| 硬矛盾率 | 经真人确认严重矛盾数 / 合格稿万字 | 同时给样本量和置信区间 |
| 检索 Recall@k | 必需证据被 Top-k 找到的比例 | 黄金集合由作者与审校员建立 |
| 污染率 | 错误候选事实进入批准 canon 的条数 / 提交总条数 | P0 可规定目标为 0 |
| 修复净成功率 | 消除原缺陷且未新增严重缺陷的 patch / 所有 patch | 需跑跨章回归 |
| 文学成对偏好 | 真人盲评 A 优于 B 的比例和置信区间 | 样本分题材，随机顺序 |
| 实际人力成本 | 作者规划 + 校对 + 改稿 + 审批分钟 / 定稿万字 | 不得只统计打字时间 |
| 综合单位成本 | 模型费用 + 计算 + 人工 + 失败重试 / 定稿万字 | 以验收质量一致为条件 |
| 数据泄露回归 | 自动尝试跨作品/跨租户取数的成功次数 | 理想条件为 0 次成功 |

**Pilot 建议：**先在两个题材、两种长度、四个方案、两个随机种子上运行 32 个小规模样本；用人工标记的硬约束缺陷和读者盲评做两套独立结果。这里的 32 是实验设计建议，不是得到统计显著性的保证；若差异小或离散大，应进行功效分析后扩大样本。

## 20. 实施计划：分三阶段，每阶段都设置止损门槛

### Phase 0｜两周量级的工程原型（时间仅为规划粒度）

**目标：**在一部 3—5 万字测试小说上证明“状态不可污染、冲突可定位、审批可回滚”。实现数据 Schema、事件日志、最小人物/物件状态机、章节契约、人工审批与 12 类失败注入。**不做：**复杂分布式微服务、全自动商业发行、海量 Agent。**退出条件：**所有测试案例都有明确判断与来源；未批准 fact 无法写入 canon；重复提交不会形成重复事件。

### Phase 1｜质量与效率验证

**目标：**增加异构关系（人物图/事件链/地点规则）、融合检索、章节局部修复、结构化叙事评价与真人盲评。将真实编辑分钟数写入数据表。**退出条件：**以对照实验说明综合成本和核心质量指标净改善；如仅换来更高模型打分但人类偏好下降，应停止扩张流程。

### Phase 2｜商业和多媒体拓展

**目标：**多人协作、租户安全、平台政策快照、版权链导出、发布 API 与有声/翻译/剧本衍生。**退出条件：**真实作者持续使用、上架合规检查得到签核、每万字合格定稿成本可控，并有可追踪的经营回款。

## 22. 结论：产品化优先序及不可声称的能力

**最优先：**先做一套“可导入已有小说的连续性检查和作者可控故事记忆平台”，因为其缺陷可以复现、成本可以计量、用户价值可用校对工时与错误率验证。**随后：**将分层规划、叙事评价、局部修复接入创作流程。**最后：**搭建跨媒介资产中台与多作者出版运营。

**必须保持的科研诚实：**不能将评估基准中的局部准确率说成全行业准确率；不能将厂商的功能列表说成效果证明；不能将 AI 检测器分数当版权证据；不能将“每秒生成字数”当作创作生产力；不能保证中文长篇的百万字水平与商业化成功，除非有相应的真实样本与对照实验证明。
